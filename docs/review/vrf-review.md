# Blind VRF for dice, in Compact — review request

Thanks for the offer to look at this. Context: a Yahtzee-style dice game on Midnight. An
operator runs the table and resolves each roll. Today it uses commit–reveal — it commits
`H(tableId, seed)` before any player exists, so it cannot _choose_ the dice, but it holds the
seed, so from the moment a seat opens its turn it can _compute_ every die of that turn before
the player has chosen a single hold. We want to remove the foreknowledge without removing the
operator.

The construction is a blind VRF with a Chaum–Pedersen DLEQ, on the native Jubjub curve, composed
from `ecMul` / `ecMulGenerator` / `ecAdd` / `hashToCurve` as you suggested.

## The protocol

One VRF key `x` per table, generated by the operator at deploy. `PK = x*G` is sealed into the
contract in place of the old seed commitment. For one roll, with `sk_s` the seat's secret
(already committed at join as `H(tableId, sk_s)`):

```
    m     = (tableId, round, rollIndex, holdMask of the previous roll, sk_s)
    P     = hashToCurve(m)          the input point — only this seat can form it
    B     = rho * P                 rho fresh and random, chosen by the player
    S     = x * B                   the operator's answer, with a DLEQ
    Gamma = rho^-1 * S = x * P      unblinded in the player's browser
    dice  = expand(H(Gamma))
```

The operator sees only `B`. With `rho` uniform that is a uniform point, and it cannot form `P`
itself because `P` needs `sk_s`. So it answers without learning the roll.

## What the contract checks, and where

The chain is split over two transactions because the operator and the player hold different
secrets, and this is the part I would most like a second opinion on.

**The operator's transaction** (`resolveRoll1` / `resolveReroll`) supplies `S` and the proof and
checks only `vrfDleqHolds(PK, B, S, a1, a2, z)`. `B` is read off the ledger, not passed in — the
operator answers the question that was asked.

**The player's next move** (`playerMove`) supplies `rho` and `Gamma` as witnesses and checks:

```
    P == vrfInputPoint(tableId, round, rollIndex, priorHoldMask, sk_s)   rebuilt from ledger state
    B == rho * P                                                          the query was this input
    S == rho * Gamma                                                      unblinds, without an inverse
```

`S == rho*Gamma` rather than `Gamma == rho^-1 * S` so no scalar inversion is needed in-circuit.

Both of the player's checks are in ONE transaction on purpose. We considered verifying `B ==
rho*P` when the query is written and only `S == rho*Gamma` at reveal, to save a hash-to-curve.
It is unsound: the contract does not store `rho` between transactions, so a player could write
the query under `rho` and reveal under `rho'`, yielding `Gamma = (rho/rho')*x*P` — a factor it
chooses freely, and therefore grindable.

`B` is on chain rather than exchanged off-chain, also on purpose: the contract admits one query
per `(seat, round, rollIndex)`, so a player colluding with the operator cannot price several
candidate holds and keep the best. Off-chain that guarantee disappears.

At settlement the contract reveals `x` and checks `x*G == PK`; a replay then recomputes each
seat's `P` from its revealed `sk_s`, then `Gamma = x*P`, then the dice, with no DLEQ needed
after the fact.

## Specific things I would value your eye on

1. **The Fiat–Shamir transcript.** `vrfChallenge` hashes `(PK, B, S, a1, a2)` — ten field
   elements, the X and Y of each. Is that the right transcript, and is omitting the generator
   and any table/round binding a problem here given `B` already commits to both?
2. **The scalar reduction.** `transientHash` returns a `Field` (~2^255) and the Jubjub scalar
   order is ~2^252, so we reduce with `as JubjubScalar`. Measured: 245 of 300 real transcript
   hashes exceed `r`. Is the resulting ~3-bit non-uniformity in the challenge acceptable, or
   should we hash-to-scalar with wide reduction instead?
3. **The derived nonce.** `vrfNonce(x, B) = H(17, x, B.x, B.y)`, so nonce reuse across two
   different queries is impossible by construction. Domain tag 17 distinguishes it from the
   challenge hash. Is deriving from `(x, B)` alone sufficient, or should the full transcript go
   in?
4. **`hashToCurve` on a 4-field preimage.** We hash in the BYTES domain first
   (`persistentHash` over four `Bytes<32>`) and then `hashToCurve` that, because
   `Bytes<32> as Field` fails at runtime for ~half of all values (256-bit value, ~2^255
   modulus). Is there a cheaper or more idiomatic way?
5. **Cofactor / subgroup.** We never explicitly clear a cofactor or check subgroup membership on
   `B`, `S`, `a1`, `a2`. Is that safe with these primitives, or should incoming points be
   validated?

## Cost

Measured with full keys, compiler 0.34.0:

| circuit                    | before (commit–reveal) | after (VRF) |
| -------------------------- | ---------------------- | ----------- |
| `resolveRoll1` (operator)  | k=15                   | **k=13**    |
| `resolveReroll` (operator) | k=15                   | **k=12**    |
| `playerMove` (player)      | k=14                   | **k=16**    |

The cost moves from the operator to the player: the resolves only check a DLEQ now, while
`playerMove` gained the hash-to-curve, two scalar multiplications and the dice ladder.

## The contract

This is the whole of the cryptographic half. The rest of the table contract uses it at the three
call sites described above.

```compact
// Blind-VRF primitives, shared by `table.compact` and the measurement contracts.
//
// The protocol is docs/vrf-dice.md; `probes/vrf` in the private repo implements the same thing
// in TypeScript over these very circuits and attacks it, including the forgery that a
// witnessed challenge would admit. Everything here is the on-chain half.
//
// THE CHALLENGE IS DERIVED, NEVER SUPPLIED. A prover free to choose `c` alongside `a1` and `a2`
// satisfies both DLEQ equations for ANY response: pick z and c, set a1 = z*G - c*PK and
// a2 = z*B - c*S, and they hold identically. That is precisely the operator-player collusion
// the DLEQ exists to stop, so `vrfChallenge` hashes the transcript the equations are about.
//
// WHY THIS NEEDS COMPILER 0.34. A transcript hash is a `Field` (~2^255) and Jubjub's scalar
// order is ~2^252, so most hashes are out of range and must be reduced before they can be a
// scalar. `as JubjubScalar` is that reduction. Measured: 245 of 300 real transcript hashes
// exceed r; on 0.31.1 every one was rejected by `ecMul` ("failed to decode for built-in type
// EmbeddedFr") and there was nothing in that toolchain to reduce them.

pragma language_version >= 0.26;

import CompactStandardLibrary;

/**
 * The VRF input point for one roll: `P = hashToCurve(tableId, round, rollIndex, holdMask, sk)`.
 *
 * `sk` is what makes `P` unformable by anyone but this seat. Everything else in it is public,
 * and a public input would let the operator evaluate the VRF for every seat in advance — the
 * blinding would then protect the wire and nothing else. `holdMask` is the PREVIOUS roll's
 * holds, which is what stops a query for roll i+1 being formed before hold i is fixed.
 *
 * HASHED IN THE BYTES DOMAIN, deliberately. `tableId as Field` and `sk as Field` are traps: a
 * Bytes<32> is a 256-bit value and the Field modulus is ~2^255, so roughly half of all real
 * values are out of range and the cast fails AT RUNTIME with "exceeds maximum value of Field
 * type" — on half the tables, and only once one is played. Field to Bytes<32> is always
 * defined, so `meta` goes that way instead. The three counters pack into one Field injectively
 * because each is a Uint<8>.
 */
export pure circuit vrfInputPoint(
  tableId: Bytes<32>,
  round: Uint<8>,
  rollIndex: Uint<8>,
  holdMask: Uint<8>,
  sk: Bytes<32>,
): JubjubPoint {
  const meta = (round as Field) * 65536 + (rollIndex as Field) * 256 + (holdMask as Field);
  return hashToCurve<Bytes<32>>(persistentHash<Vector<4, Bytes<32>>>([
    pad(32, "dust-dice:v2:vrf-input"),
    tableId,
    meta as Bytes<32>,
    sk,
  ]));
}

/** The Fiat-Shamir challenge over the whole DLEQ transcript. See the header. */
export pure circuit vrfChallenge(
  pk: JubjubPoint,
  blinded: JubjubPoint,
  response: JubjubPoint,
  a1: JubjubPoint,
  a2: JubjubPoint,
): Field {
  return transientHash<Vector<10, Field>>([
    jubjubPointX(pk), jubjubPointY(pk),
    jubjubPointX(blinded), jubjubPointY(blinded),
    jubjubPointX(response), jubjubPointY(response),
    jubjubPointX(a1), jubjubPointY(a1),
    jubjubPointX(a2), jubjubPointY(a2),
  ]);
}

/**
 * Chaum-Pedersen: the key behind `pk` is the one that produced `response` from `blinded`.
 *
 * Written as `z*G == A1 + c*PK` rather than `A1 == z*G - c*PK` so that no negation is needed.
 * Returns true/false rather than asserting, so the caller words the failure in its own terms.
 */
export pure circuit vrfDleqHolds(
  pk: JubjubPoint,
  blinded: JubjubPoint,
  response: JubjubPoint,
  a1: JubjubPoint,
  a2: JubjubPoint,
  z: Field,
): Boolean {
  const c = vrfChallenge(pk, blinded, response, a1, a2);
  const first = ecMulGenerator(z as JubjubScalar) == ecAdd(a1, ecMul(pk, c as JubjubScalar));
  const second = ecMul(blinded, z as JubjubScalar) == ecAdd(a2, ecMul(response, c as JubjubScalar));
  return first && second;
}

/**
 * The 32 bytes a roll's dice are expanded from: `H("dust-dice:v2:roll", H(gamma.x, gamma.y))`.
 *
 * Deliberately the same shape as the seed-era digest so the ladder in `dice-core` is unchanged
 * — only where the 32 bytes come from moves.
 */
export pure circuit vrfRollDigest(gamma: JubjubPoint): Bytes<32> {
  return persistentHash<Vector<2, Bytes<32>>>([
    pad(32, "dust-dice:v2:roll"),
    persistentHash<Vector<2, Field>>([jubjubPointX(gamma), jubjubPointY(gamma)]),
  ]);
}

/** Pack a hold mask into the byte the VRF input commits to. Position i is bit i. */
export pure circuit packHoldMask(mask: Vector<5, Boolean>): Uint<8> {
  const b0 = mask[0] ? 1 : 0;
  const b1 = mask[1] ? 2 : 0;
  const b2 = mask[2] ? 4 : 0;
  const b3 = mask[3] ? 8 : 0;
  const b4 = mask[4] ? 16 : 0;
  return (b0 + b1 + b2 + b3 + b4) as Uint<8>;
}

// ---------------------------------------------------------------------------------------
// The curve operations, exported so the OFF-CHAIN halves can be built from the contract's own
// arithmetic rather than a second implementation of Jubjub.
//
// The operator needs `S = x*B`, `A1 = k*G` and `A2 = k*B`; the player needs `B = rho*P` and
// `Gamma = rho^-1 * S`. Reimplementing those in TypeScript is how this class of protocol
// usually dies — a curve detail differs, and the failure surfaces as "invalid proof" with
// nothing pointing at the arithmetic. These are pure circuits, so they carry no verifier key
// and do not count against the nine-circuit deploy ceiling (bugs-found.md #16).
// ---------------------------------------------------------------------------------------

/** `s * p`. The scalar is reduced mod r, as everything else here does. */
export pure circuit vrfScalarMul(p: JubjubPoint, s: Field): JubjubPoint {
  return ecMul(p, s as JubjubScalar);
}

/** `s * G`. Used for the public key and for the DLEQ's first commitment. */
export pure circuit vrfGeneratorMul(s: Field): JubjubPoint {
  return ecMulGenerator(s as JubjubScalar);
}

/** `a + b`. */
export pure circuit vrfPointAdd(a: JubjubPoint, b: JubjubPoint): JubjubPoint {
  return ecAdd(a, b);
}

/**
 * The DLEQ nonce, derived rather than drawn: `k = H("nonce", x, B)`.
 *
 * REUSING A NONCE ACROSS TWO ANSWERS REVEALS `x`. Two proofs with the same `k` and different
 * challenges give `z1 - z2 = (c1 - c2)*x`, and `x` falls straight out — after which any player
 * who knows its own `sk` can compute its own future rolls for every candidate hold and choose
 * with foreknowledge, which is the whole property this scheme exists to deny. On-chain query
 * counting does not help there, because nothing is being asked.
 *
 * So the nonce is not a parameter the operator can get wrong. Deriving it from the secret and
 * the query makes reuse across two DIFFERENT queries impossible by construction, and reuse on
 * the SAME query harmless: it reproduces the identical proof, which is the same answer to the
 * same question. It also removes any dependence on the quality of the operator's RNG.
 *
 * `x` is in the hash, so the nonce is unpredictable to everyone who does not already hold `x`.
 */
export pure circuit vrfNonce(secret: Field, blinded: JubjubPoint): Field {
  return transientHash<Vector<4, Field>>([
    // A distinct domain from `vrfChallenge`, so a nonce can never collide with a challenge.
    17 as Field,
    secret,
    jubjubPointX(blinded),
    jubjubPointY(blinded),
  ]);
}
```

## Test

A TypeScript harness drives all three parties over these same pure circuits — no second Jubjub
implementation, so the operator's arithmetic and the circuit's cannot drift — and attacks the
result. The attack that matters:

> Given a free choice of `c`, a colluding operator picks any response it likes, then solves for
> `a1` and `a2`: set `a1 = z*G - c*PK` and `a2 = z*B - c*S` and both DLEQ equations hold
> identically. An earlier draft of this circuit took `c`, `a1` and `a2` as witnesses and would
> have accepted it. The test builds that forgery, asserts that it _does_ satisfy both equations,
> and then shows the circuit rejecting it — which it can only do because `vrfChallenge`
> recomputes `c` from the transcript.

Also covered: a response computed under a different key is refused; the operator's transaction
demonstrably contains no dice; a held die survives a reroll; and two different queries never
share a nonce commitment.

## Update, 2026-09-21 evening — the resolve became an oracle post

Nothing above about the cryptography changed: the input point, the blinding, the DLEQ with the
in-circuit Fiat–Shamir challenge and the deterministic nonce are exactly as written. What changed
is _where the answer lands_, forced by a ledger rule rather than by the VRF.

**The rule.** Ledger 9 executes every call's guaranteed transcript before any call's fallible one
and rejects a merged transaction in which a guaranteed call follows a fallible one, in (segment,
position) order. The ledger classes each whole call itself by size: a resolve is small enough to
be guaranteed, `playerMove` is not. A fast table settles a turn as ONE transaction of up to seven
merged calls, so its three resolves must be able to run first, against a state none of the turn's
moves has touched — which is only sound if a resolve reads nothing a move writes.

**The shape now.** One circuit, `resolveRoll(seat, rollIndex, round, blinded, response, dleqA1,
dleqA2, dleqZ)`: it reads `phase`, `seatCount` and the sealed `vrfPublicKey`, verifies the DLEQ
for the `blinded` it was _given_, and writes `vrfAnswer[seat*3 + rollIndex] = {round, blinded,
response}`. It does not read the seat's turn and does not advance its stage. The player's next
move reads that cell and asserts, before anything else, that `cell.round == turn.round` and
`cell.blinded == turn.blinded` — the query this seat actually committed — and only then checks
`B = ρ·P` and `S = ρ·Γ` as before. So the binding "the operator answered THIS seat's THIS query"
moved from the resolve to the move that spends the answer, one call later, where it is asserted by
the party the answer is for.

**A sixth question for you.** The resolve now proves a DLEQ for _any_ point it is handed. An
operator can post `S = x·B'` for a `B'` nobody asked; no move will ever match it, and the cell is
overwritten by the next honest answer. I believe this is harmless — the DLEQ's soundness is
per-point, `x` is never exposed by answering arbitrary points (that is the OPRF's blindness in the
other direction), and one query per (seat, round, rollIndex) is still enforced by the move that
committed it. Is there an argument I am missing for why an oracle that answers unsolicited points
weakens anything?

Verified on a local ledger-9 devnet: a two-seat 13-round game replays 1148/1148 checks from the
revealed key and the revealed seat secrets, including, per roll, that the answer cell holds the
seat's re-derived query and `x` applied to it; a fast table settled two seven-call turns in one
transaction each.
